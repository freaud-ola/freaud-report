01 · 方案概述

面向数仓的 AI 原生 智能平台

从 Hive Metastore 自动采集血缘、表结构、统计信息等元数据，构建数仓专属知识库， 并在此基础上部署四类智能工作流，将人工重复作业转化为 AI 自动化能力。

🗂️
元数据知识库
从 Hive Metastore 实时采集表结构、血缘依赖、分区信息、统计指标，向量化存储供 AI 检索。
📊

Agent 定时拉取调度日志与质量指标，自动生成可读性强的 HTML/Markdown 分析报告，无需人工介入。
💬
智能问数 Text-to-SQL
用户用自然语言描述需求，Agent 结合元数据上下文生成准确 HiveSQL，支持多轮澄清与执行验证。
🤖
对话式知识问答
面向业务人员的问答入口，支持"这张表是什么意思""字段 xxx 怎么算的"等自然语言查询。
🔍
数据质量监控
持续监控表数据新鲜度、空值率、异常值，通过 Agent 自动归因并推送告警摘要。
🔗
血缘影响分析
当上游表变更时，Agent 自动遍历下游血缘链路，生成影响范围报告及变更建议。

03 · 核心模块详解

四大 核心工作流

每个模块独立可部署，可按优先级逐步落地，共享底层知识库与 LLM 服务。

核心思路：从 Hive Metastore 提取结构化元数据（表名、字段、注释、分区、血缘、统计信息）， 转化为自然语言描述文档后向量化存储，形成数仓专属知识图谱。 这是所有 Agent 能力的基础底座，数据质量直接决定上层应用效果。

STEP 1
连接 Hive Metastore，全量抽取元数据
通过 PyHive / Thrift API 连接 HMS（Hive Metastore Server），按库/表/字段逐层抽取：表基础信息、字段类型与注释、分区列定义、表存储格式、HDFS 路径与文件大小统计。同时抽取 Airflow DAG 中的依赖关系构建血缘图。
PyHive Thrift API SQLAlchemy NetworkX 血缘图
# 连接 HMS 抽取表元数据示例 from pyhive import hive import json conn = hive.connect(host='hive-metastore', port=10000) cursor = conn.cursor() # 获取所有表的字段 + 注释 cursor.execute(""" SELECT t.TBL_NAME, c.COLUMN_NAME, c.TYPE_NAME, c.COMMENT FROM TBLS t JOIN COLUMNS_V2 c ON t.CD_ID = c.CD_ID WHERE t.DB_ID = (SELECT DB_ID FROM DBS WHERE NAME = %s) """, (db_name,)) rows = cursor.fetchall()
STEP 2
元数据文档化 —— 结构化 → 自然语言
将原始元数据转换为标准化的"表描述文档"，包含表的业务用途（从注释/Wiki推断）、字段说明、典型 SQL 使用示例、上下游血缘摘要等，每张表生成一份 Markdown 文档作为 RAG 的原始语料。
Jinja2 模板 LLM 注释补全
# 自动生成表描述文档模板 TEMPLATE = """ # 表：{db}.{table} **业务描述**：{desc} **所属分层**：{layer} | **负责人**：{owner} **分区字段**：{partitions} | **更新频率**：{cron} ## 字段说明 {fields_md} ## 上游依赖 {upstream} ## 典型查询示例 {sql_examples} """
STEP 3
向量化存储 —— 三层知识库
按用途分三层存储，召回时按 Layer 路由，避免相互干扰：
① 表级知识库：每张表的完整描述，支持"找到某类数据"的语义检索；
② 字段级知识库：细粒度字段含义、枚举值说明，支持 SQL 生成时列名匹配；
③ 血缘知识库：以自然语言描述血缘路径，支持影响分析问答。
Milvus 向量库 BGE-M3 Embedding Hybrid Search
STEP 4
增量同步 —— 元数据变更监听
监听 HMS 的 DDL 事件（表增删改、字段变更），通过 Hive Metastore Hook 或定时对比方式捕获变更，触发对应向量块的更新/删除，确保知识库与实际元数据保持一致，通常延迟 ≤ 15 分钟。
Airflow 定时 Change Detection
抽取的核心元数据字段
  • 表基础信息：db_name、table_name、owner、create_time、table_type、storage_format
  • 字段信息：column_name、data_type、comment、nullable、is_partition
  • 统计信息：row_count、file_size、last_ddl_time、num_files、num_partitions
  • 血缘关系：upstream_tables、downstream_tables、lineage_depth
  • 调度信息：job_name、cron_expr、avg_duration、sla_threshold
  • 质量信息：null_rate、max_val、min_val、last_check_time
知识库分层与召回策略
  • L1 全局层：库级别摘要，用于"哪个库有XX数据"类问题，topK=3
  • L2 表级层：表描述+字段摘要，用于 SQL 生成时选表，topK=5~10
  • L3 字段层：字段级别精确匹配，用于列名补全，topK=15
  • 混合检索：语义向量搜索 + BM25 关键词检索，RRF 融合排序
  • 重排序：Cross-Encoder 对 topK 结果精排，过滤低相关文档
  • 缓存：热点查询结果 Redis 缓存，TTL 1小时

核心思路：Agent 作为"自动化报告员"，在 Airflow 中作为 Task 嵌入现有调度流水线。 每次调度周期结束后，Agent 自动拉取质量指标、运行日志、SLA 达成情况， 结合历史对比，生成结构化报告并推送。人工只需审阅结论，不再手动整理数据。

STEP 1
触发条件 —— 事件驱动 + 定时双模式
支持两种触发：① Airflow DAG 的 on_success_callback，在调度周期完成后自动触发报告生成 Agent；② 定时触发（每日 10:00）生成前一天的汇总报告。Agent 接收上下文参数（日期范围、库名范围、关注指标）。
Airflow CallbackCron Trigger
STEP 2
数据采集工具调用 —— Agent Tool Use
Agent 按需调用注册好的工具函数采集指标：

STEP 3
LLM 撰写报告正文
将采集的结构化数据 + 历史对比数据注入 Prompt，LLM 按固定报告模板生成自然语言叙述，包括：总结摘要、异常归因、优化建议、优先级排序。所有数字均由工具函数提供，LLM 只负责"写作"不负责"算数"。
Structured OutputJSON Schema
STEP 4
报告渲染与推送
生成的报告内容渲染为 HTML（复用当前项目的报告模板），同时推送：① 企业微信/钉钉 Webhook（摘要卡片）；② 邮件（完整 HTML 报告）；③ 持久化到对象存储（OSS/S3），提供历史报告查阅。
HTML Report企微 WebhookEmail SMTP
报告覆盖的分析维度
  • SLA 完成情况：各库各层完成率、超时作业、P90 耗时趋势
  • 资源消耗：内存/核时 Top 10，与上期对比变化量
  • 调度 Gap：冗余等待作业识别，调整建议
  • 数据质量：空值异常、行数波动、分区断档检测
  • 血缘风险：高下游依赖作业延迟风险预警
  • 优化 ROI：与历史基准期对比改进量化
报告质量保障机制
  • 数字来源标注：所有数字附来源工具名，可追溯
  • Hallucination 防护：LLM 禁止凭空生成数字，仅基于工具返回数据
  • 自动审核：报告中数字与原始数据做一致性校验，不通过则回滚人工
  • A/B 对比：新旧两版报告生成流程并行运行，人工验收后再切换
  • 人工审核入口：报告含"异议反馈"链接，修正结果用于微调

核心思路：Text-to-SQL 是本方案技术难度最高的模块。 通过 RAG 检索相关表结构注入 Prompt，结合 Schema Linking（将问句中实体映射到实际字段）， 生成符合 HiveSQL 规范的查询语句，并在沙箱环境执行验证，实现"一问一 SQL"。

STEP 1
问题理解与实体识别
对用户输入进行 NLU 处理：识别时间范围（"上周"→具体日期）、业务实体（"GMV"→对应字段）、聚合方式（求和/均值/分组）、过滤条件（"dws_pa 库"）。必要时主动追问澄清，如"您说的用户是指注册用户还是活跃用户？"
Intent ClassificationEntity ExtractionTime Normalization
STEP 2
Schema Linking —— 找到相关表和字段
用识别出的实体检索向量知识库，获取 Top-K 候选表；对候选表中的字段做二次相似度匹配，过滤不相关字段。最终构建精简版 Schema 上下文（仅包含相关列），避免 Prompt 过长。
# Schema Linking 核心流程 user_query = "查询上周 dws_pa 库中每个渠道的新增用户数" # 1. 向量检索候选表 candidates = vector_store.search(user_query, collection="table_level", top_k=8) # 2. 字段级精确匹配 schema_ctx = build_schema_context(candidates, user_query) # → 仅保留: dws_pa.user_daily_new(channel, new_user_cnt, dt) # 3. 注入 Prompt 生成 SQL sql = llm.invoke(SQL_PROMPT.format(schema=schema_ctx, query=user_query))
Vector SearchField Matching
STEP 3
SQL 生成 —— HiveSQL 规范约束
Prompt 中注入 HiveSQL 编写规范约束（本项目的 user_rules），要求：大写关键词、必须带 dt 分区过滤、不允许 SELECT *、聚合层使用 CTE。 生成后自动做语法检查（EXPLAIN 语句）。
HiveSQL RulesEXPLAIN CheckCTE Style
STEP 4
沙箱执行验证 + 结果解读
在只读 Hive 账号下执行生成的 SQL（限制 LIMIT 1000），若执行成功则将结果数据交给 LLM 用自然语言解读（"上周各渠道中，App 渠道新增用户最多，达 12.3万"）；若执行失败则将报错信息反馈给 Agent 进行自我修正（最多 3 次重试）。
Read-Only ExecutionSelf-Correction
Text-to-SQL 准确率提升策略
  • Few-shot 示例：在 Prompt 中注入 3~5 个领域内高质量 SQL 示例
  • Self-consistency：生成 3 个候选 SQL，投票选最稳定的一个
  • Schema Filter：精减 Schema 只保留相关字段，减少干扰
  • SQL 微调：收集人工纠错样本对 LLM 进行 LoRA 微调（迭代优化）
  • Fallback：置信度低时，展示 SQL 草稿请用户确认后再执行
  • 业务词典：维护"GMV→order_amount、DAU→active_user_cnt"映射表
安全与权限控制
  • 只读账号：Agent 使用专用 Hive 只读账号，无 INSERT/DROP 权限
  • SQL 白名单：只允许 SELECT，拦截 DDL/DML/LOAD 等危险语句
  • 资源限制：每次查询限制 LIMIT 1000、execution_timeout 60s
  • 数据脱敏：结果中的 PII 字段（手机、邮箱）自动脱敏后返回
  • 操作审计：所有 SQL 执行记录入审计日志，可追溯到用户

核心思路：面向业务人员的低门槛知识问答入口。 用户不需要懂 SQL，直接用中文提问"xxx 表是干什么的""dws_pa 和 ods_pa 有什么区别" "某个指标最近为什么波动"，Agent 从知识库检索并组织自然语言答案。

05 · 实施路线图

四阶段 渐进式 落地

每个阶段交付独立可用的能力，不依赖后续阶段完成，降低实施风险，尽早产生价值。

第一阶段 · 第 1~4 周
基础设施 & 知识库
  • 搭建 Milvus + PostgreSQL 基础设施
  • 完成 Hive 元数据全量采集脚本
  • 实现表/字段描述文档生成
  • 完成向量化存储（三层知识库）
  • 验证检索召回准确率 ≥ 80%
  • 搭建 FastAPI 基础服务框架
第二阶段 · 第 5~8 周
对话问答 & Text-to-SQL MVP
  • 实现基础 Q&A 问答链（RAG）
  • 上线企业微信机器人入口
  • Text-to-SQL 单表查询能力
  • SQL 沙箱执行验证机制
  • 开始收集用户反馈样本
  • 单表 SQL 准确率目标 ≥ 70%
第三阶段 · 第 9~12 周
自动化报告 & 多表 SQL

06 · 风险评估

风险识别与 应对策略

提前识别主要风险点，制定缓解措施，避免实施过程中出现不可控情况。

风险点 等级 风险描述 应对策略
元数据注释质量差 高 大量表/字段无中文注释，影响 RAG 检索质量和 LLM 理解准确率 ① 用 LLM 结合表名 + 字段名 + 示例数据自动补全注释；② 建立注释质量评分机制，低分表人工优先补录；③ 接受部分准确率损失，随注释改善迭代
LLM Hallucination 高 SQL 生成或问答中 LLM 捏造不存在的表名、字段名，导致执行失败或数据错误 ① Text-to-SQL 强制走 Schema Linking，LLM 不得创造新字段；② 所有数字必须来源于工具调用结果；③ SQL 执行前做语法 + Schema 合法性校验；④ 置信度低时展示原始上下文供用户核查
API 成本失控 中 高频问答导致 LLM API 调用量超预期，月度成本超出预算 ① 热点问题答案缓存（Redis TTL 1小时）；② Prompt 精简，控制 token 消耗；③ 设置每用户每日调用配额；④ 非敏感问答可路由至小模型（Qwen-7B）降成本
数据安全合规 中 元数据（表名、字段）通过 LLM API 出境；SQL 执行可能返回敏感数据 ① 优先选用支持私有化部署的 LLM（Qwen/DeepSeek）；② 若使用云 API，对表名/字段名做脱敏替换后再传入；③ SQL 结果中 PII 字段自动遮盖；④ 通过数据安全团队的合规审查
Hive 查询资源占用 中 Text-to-SQL 大量查询请求可能影响生产 Hive 集群稳定性 ① 使用独立只读 Hive 账号，配置专用 YARN 队列；② 强制加 LIMIT 上限 + 执行超时（60s）；③ 查询结果缓存，同一 SQL 24小时内不重复执行；④ 非工作时间批量预计算热点查询
团队 AI 接受度 低 用户对 AI 生成内容不信任，或认为准确率不够高而不愿使用 ① 答案来源透明可溯，增强信任；② 设定合理预期（非100%准确的助手）；③ 从内部工程师开始推广，收集正向反馈案例；④ 发布准确率指标看板，持续公示改进进展
